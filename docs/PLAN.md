## 0. 已定决策记录

| 决策 | 结论 |
|---|---|
| 核心逻辑 | **挑菜为主**（灵感加入本周 → 我的食材过滤 → 排出 → 营养门闩 → 具名清单），食材驱动（勾选）作为辅助入口；两者共享同一套底层引擎 |
| MVP 范围 | V0.1 不做美团链接解析，用内置食材库跑通全流程；超市对接放 V0.2/V0.3 |
| 技术栈 | 纯前端 PWA（Next.js + TypeScript + Tailwind），无后端、无账号，用户数据存本地 |
| 协作方式 | 全程在 Cursor 中开发，不建 .agent 交接协议；规划与验收由规划 AI 负责，编码由执行 AI 按 SPEC 实施 |
| 排餐单位 | 一道食谱 = 完整一餐（含主食），固定 1 人份不缩放，营养误差由"微调件"补齐 |

| 营养数据源 | 以 USDA FoodData Central 为主（公共领域，无版权风险）；娃娃菜/山药/料酒等中国特有食材参考中国食物成分表 |
| 数据文件形态 | V0.1 用聚合文件 `data/ingredients.json` + `data/recipes.yaml`，V0.3 社区化时再拆分 |

## 1. 产品定位

**一句话**：告诉我你家楼下超市有什么，我告诉你买什么、怎么吃。

**目标用户**：想吃健康餐（减脂/增肌/维持）但不会规划营养、不知道买什么、做饭能力弱的人。

**差异化**：从"你能买到的食材"出发（而非从菜谱出发），并且照顾真实生活约束——厨具有限、食材会坏、超市按盒卖不按克卖。

**边界**：不做交易、不做下单、不做社交。只做决策助手。

## 2. 双模式设计（共享引擎）

两种模式共用底层引擎，仅入口顺序不同：

```
共享引擎：
  食材库 ──┐
  食谱库 ──┼─→ 营养计算器 → 排餐求解器 → 清单生成器
  用户档案 ─┘

模式 A（食材驱动，**辅助**）：本周货架 → 在篮内约束下排餐 → 出清单
模式 B（食谱驱动，**默认主路径**）：灵感挑菜 → 我的食材过滤 → 排出 → 营养门闩 → 具名清单
```

### 模式 A：食材驱动（辅助入口）

1. 建档完成后进入**食材篮**页。系统按营养目标预填推荐篮（按蛋白源/碳水源/蔬菜/脂肪源/微调件分组），用户像逛货架一样增删。
2. **实时反馈面板**（防掉坑的关键）：每次增删食材，立即显示——
   - 当前篮子可做出的食谱数量；
   - 可覆盖的天数与每日营养达成度（热量/蛋白/脂肪/碳水，目标 ±10%）；
   - 凑不齐时给**最小补充建议**："再加鸡蛋可解锁 5 道菜 / 补齐早餐蛋白"。
3. 确认篮子 → 求解器仅在篮内食材中排餐 → 生成餐单与采购清单。
4. 不允许确认一个"做不成足够多菜"的篮子（按钮置灰 + 提示补什么）。

推荐算法要点：预填推荐从**高覆盖食材**出发（在食谱库中出现频率高的食材优先），保证默认篮一定可解。

### 模式 B：食谱驱动（辅助入口）

浏览/搜索食谱库（按厨具、时长、口味过滤）→ 手动加入餐单 → 系统检查营养缺口并自动补齐剩余餐位 → 反推采购清单。

### V0.2 超市导入与模式 A 的关系

美团商品导入的结果 = **食材篮的可选范围预过滤**（篮子里只出现你家附近真的能买到的东西）。模式 A 的交互不需要为 V0.2 重构，这是坚持食材驱动的架构红利。

## 3. 完整用户流程（V0.1）

```
① 建档向导
   输入：性别 / 年龄 / 身高 / 体重 / 活动水平（5 档）/ 目标（减脂/增肌/维持）
        / 忌口与过敏 / 厨具清单（电饭煲、空气炸锅、微波炉、燃气灶、烤箱、无火）
   输出：每日热量与宏量目标
② 定范围
   买几天的量（1–7 天）+ 勾选家里已有食材及数量
③ 装篮（模式 A）或挑菜（模式 B）
④ 排餐预览
   N 天 × 每天 2–3 餐；每日营养达成度条；易腐食材排前几天；
   缺口用"微调件"补齐建议（无糖酸奶 +10g 蛋白、坚果一把 +15g 脂肪等）
⑤ 采购清单
   汇总食材 − 已有存货 → 向上取整到包装规格（"鸡胸肉 900g ≈ 3 盒"）
   → 标注储存提示（"买回当天分装冷冻"）→ 用户自行下单
⑥ 跟做视图
   按天/按餐展示食谱：≤5 步、标注厨具与用时、克数直接给到"生的称多少"
```

## 4. 营养计算规范

- **BMR**（Mifflin-St Jeor）：
  - 男：`10×体重(kg) + 6.25×身高(cm) − 5×年龄 + 5`
  - 女：`10×体重(kg) + 6.25×身高(cm) − 5×年龄 − 161`
- **TDEE** = BMR × 活动系数（久坐 1.2 / 轻度 1.375 / 中度 1.55 / 高强度 1.725 / 极高 1.9）
- **目标热量**：减脂 = TDEE × 0.8；增肌 = TDEE × 1.1；维持 = TDEE
- **安全下限**（硬约束）：女 ≥ 1200 kcal/天，男 ≥ 1500 kcal/天，触发时给出提示
- **蛋白质**：减脂 1.8–2.2 g/kg；增肌 1.6–2.0 g/kg；维持 1.2–1.6 g/kg
- **脂肪**：约占总热量 25%（不低于 0.8 g/kg）
- **碳水**：剩余热量 ÷ 4
- **附带指标**：膳食纤维仅作展示参考（25–35 g/天）；钠指标 V0.1 不做（校对成本高，延后）
- **微量元素**：V0.1 不做，后续版本再评估

精确公式、取整顺序与单测期望值见 SPEC §4。

## 5. 数据模型

类型与 schema 定稿见 **SPEC §3 / §9**（本节早期草案已废弃，主要变化：`topping` 类别改为 `seasoning` + `microAdjust` 布尔字段；`allergens` 挂在食材上而非食谱上；食谱营养由食材数据推导，CI 校验）。

**真实数据已就位，编码阶段直接消费、不得改数值**：

- `data/ingredients.json`：53 种食材（14 蛋白 / 12 碳水 / 14 蔬菜 / 5 脂肪 / 8 调味），营养为 USDA 参考值（待校对），含包装规格、保质期、过敏原；
- `data/recipes.yaml`：30 道完整一餐食谱（8 早餐 / 22 午晚餐），每道 ≤5 步、标注厨具与用时，热量区间 293–549 kcal。

用户侧数据（档案、存货、食材篮、餐单）存 localStorage，不上传。

## 6. 排餐求解器思路（V0.1 用简单贪心即可）

输入：候选食谱集合（已按食材篮/忌口/厨具过滤）、天数、每日营养目标。

1. 按餐位（早/午/晚）逐天贪心填充：优先选择能让当日营养向目标靠拢最多的食谱；
2. 约束：同一食谱一周内出现 ≤3 次（避免连吃一周同一道菜）；易腐食材的食谱排前几天；
3. 每日误差 > ±10% 的部分 → 生成微调件建议而不是死循环求解；
4. 无解时（篮子太小）→ 返回最小补充食材建议（贪心：加哪一样食材能解锁最多候选食谱）。

V0.1 不追求最优解，够用、可解释即可；后续再考虑换 ILP/启发式。打分函数、约束参数与微调件标准份定稿见 SPEC §5。

## 7. 里程碑与任务拆解

### V0.1 MVP（目标 2–3 周）

> 逐条实施规格、依赖白名单、测试期望值与完成定义见 **`docs/SPEC.md`**，执行编码以 SPEC 为唯一任务来源。

1. **脚手架**：Next.js + TS + Tailwind，静态导出，PWA manifest，ESLint/Prettier，Vitest
2. **数据层**：食材/食谱 schema（zod）+ 构建前校验脚本；数据文件已提供（53 食材 + 30 食谱），只需实现校验与加载
3. **领域逻辑**：营养计算器（含安全下限）；排餐求解器；清单生成器（扣存货、包装换算、储存提示、微调件）
4. **页面**：建档向导 → 食材篮（模式 A，实时反馈面板）→ 食谱库浏览（模式 B）→ 排餐预览 → 采购清单 → 跟做视图
5. **持久化**：localStorage 读写与版本迁移
6. **部署**：GitHub Pages 或 Vercel + GitHub Actions（lint / test / schema 校验）

### V0.2 超市手动导入

- 粘贴美团超市商品页文本 → 规则 + LLM（用户自带 API key）解析为"可买食材 + 价格"
- 食材篮按可得性过滤；采购清单显示预估花费；预算约束（可选）
- 截图 OCR 导入（可选，视文本导入效果）

### V0.3 自动化与社区

- 美团分享链接自动解析**技术验证**（允许失败，降级到 V0.2 手动导入）
- 社区食谱贡献流程：PR 模板 + schema/营养 CI 校验 + 贡献指南
- 多超市（盒马、小象）、README 英文版、LICENSE 定稿

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 美团抓取不可行/被风控（**未验证**，V0.3 才碰） | MVP 不依赖；始终保留手动导入降级路径 |
| 食材驱动下用户篮子凑不成菜 | 实时反馈 + 最小补充建议 + 不可确认无解篮子 |
| 食谱库冷启动质量 | 首批 30 道已在规划阶段产出（步骤**未实做验证**），发布前抽样实做；难度只收 1–2 级 |
| 营养数据不准 | 以 USDA FoodData Central 为主（公共领域、无版权风险），`source` 字段必填；当前为参考值，发布前逐条校对 |
| 排餐凑不齐指标 | ±10% 容差 + 微调件机制，不死磕求解 |
| 极端身体数据算出危险热量 | 安全下限硬约束 + 提示就医/咨询专业人士 |

## 9. 未验证事项

- 美团（含盒马/小象）任何形式的数据获取均**未做技术验证**，V0.2 的"复制商品页文本"是否顺畅也需真机验证；
- 营养公式参数（缺口比例、蛋白系数）为行业常用值，未经本项目用户实测校准；
- `data/ingredients.json` 的 53 条营养数值为参考值，未逐条对照 USDA 原始条目核验；
- `data/recipes.yaml` 的 30 道食谱步骤与用时为参考做法，未实际烹饪验证；
- 2–3 周的 V0.1 工期为估算。
